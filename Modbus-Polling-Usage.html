ModbusPolling：到点就采，系统替我跑

配置好「该多久跑一次」之后，任务表 + 内存时间轮 + 一个调度循环替你把服务方法按时采一遍。 这份文档讲 它怎么把定义变成任务、怎么定时派发、怎么认领不打架，以及那个唯一的查询接口。 完整口径见 Modbus-Service-Poller.md,这里是对着代码走读。

存储 modbus / polls 调度 ModbusPollingScheduler 时刻 ModbusPollingSchedule 任务 ModbusPollingPlan 对账 ModbusPollingReconciler 接口 GET /matrix/v1/modbus/polling/{spaceId}
一句话记住它

一个 jar 双部署:api N 副本不采(缺省),poller 1 副本采——靠 modbus.poll.enabled (缺省 false)区分。写到库里的就是反向契约:任务表 modbus/polls 一行的 nextRunAt 就是「下次该跑的时刻」,调度按它来、接口按它看,谁都能查、谁都能抢。

①先看全貌:定义怎么变成一次采集

下面把「配置入表 → 定时派发 → 认领执行 → 写回状态」串起来,后几节逐个展开。

图 1 · 定义入表 → 调度派发 → 认领执行 → 写回状态;右上是查询接口与多副本抢租约

②它是什么:三样东西

  • 任务表(persisted):集合 modbus/polls,一行一个「方法该多久跑一次 + 上次跑成什么样」。 字段 serviceId / pollIndex / did / interval / nextRunAt / leaseOwner / leaseUntil / lastRunAt / lastStatus / lastError / failCount。
  • 内存时间轮(in-memory):调度循环里的一张小表,只活在 poller 进程,拿任务、限流、按设备串行都用它。
  • 对账(reconcile):让库表和内存时间轮跟着服务定义走——定义改了规矩就改,幂等重算不怕丢事件。
任务表不落「运行时态」?落一部分

任务行里 nextRunAt / leaseOwner / leaseUntil / lastRunAt 等就是给「谁在跑、何时再跑」落库的; inFlight / queueSize / busyDevices 这类本进程的内存读数则不落库——接口里它们只对 poller 副本有意义。

③定义 → 任务:三条入表口径

ModbusPollingPlan 纯函数,判断「哪些方法该被轮询」并把一份定义展开成任务清单。入表三条同时成立:

  1. interval != null(配了周期);
  2. polling != false(三态:null = 有周期即跑,false = 留着周期先不跑);
  3. 请求帧是读功能码(fc 01/02/03/04)。
第三条与校验器重复,是故意的

校验器管「写进来的定义合不合规」,这里管「库里已经存在的定义能不能被定时器跑」。历史数据、直接改库、 将来放宽校验,都能让一份写方法带着 interval 出现在库里——而让服务端定时往寄存器里写值是危险动作, 判定最后一道闸必须在执行侧,不能只在写入侧。所以这里对 request 一律空值安全。

任务清单的 _id 在计划里就生成(内存时间轮的任务放进去那一刻就得有 id——抢租约、写结果、认领都靠它), 库里已有这一行时以行上的 _id 为准。did / interval 冗余进任务表只为调度: 按设备串行、算下一次时刻都不必回查定义。

④时刻算法:不漂移、错过不补、抖动

ModbusPollingSchedule 纯函数,三条口径在调度循环与单测共用同一份:

口径做法为什么
不漂移基准 = 上一次开始跑时刻 + interval,不是「跑完 + interval」否则一次慢应答(2 秒)会让周期变 interval + 耗时,长期慢慢跑偏
错过不补基准已过期(停机/新增)时,只排一次、从当下起算完整周期补跑没意义——那些时刻的值已经采不到了,连跑只会堵 RS485 总线
抖动±10%(缺省)周期,只加在重排结果上,不拉到当下/过去同一定义里的周期常是同一整数,不抖就整点齐发;拉到过去会让时间轮空转

几个入口:首次入表 insertRunAt(不立刻跑,避免对账一次加一批同时上总线)、启动恢复 restoreRunAt (按库里 lastRunAt 接着排,不是从头——否则滚动发布会把任务全挤到同一秒爆发;停机错过的返回 now)、 采集后重排 nextRunAt(锚在 runStartAt,周期不被耗时吃掉)。到期判定 isDue(闭区间)与 租约 leaseExpired / leaseClaimable 都在这。

⑤调度循环:一个线程表 + 一池工人

ModbusPollingScheduler 的 tick()(单线程 scheduleAtFixedRate,唤醒粒度 wakeup-millis 缺省 1s) 每轮:

  1. 需要的话全量对账(被写入路径置脏,或距上次对账超过 reconcile-seconds 缺省 300s);
  2. 从内存时间轮取「到点、且设备不忙」的任务;
  3. 逐个认领(claim:租约 + 前推 nextRunAt + 记 lastRunAt,一次原子写); 认领不到 = 别的副本在跑,直接重排、不计失败;
  4. 认领到的丢给工作线程池:invokePolled 调一次 → 写回结果状态 → 回填下一次时刻。
认领那一刻就落库前推 nextRunAt:一次崩溃不会立刻重跑

任务在「派发那一刻」就前推并写库,而不是「采完」才写。于是进程崩溃时,那个任务不会按旧时刻立刻重跑, 而只会多等一个周期——把「忙死」错成「正确补采一次」是时序 bug。

线程模型(改代码前先读)

  • 调度线程(单线程 ScheduledExecutorService):独占内存时间轮(不加锁)与任务对象的全部字段。 工作线程只读 ownerId/serviceId/pollIndex,算好的下一次时刻回填给调度线程,不直接改时间轮。
  • 工作线程池:modbus.poll.concurrency(缺省 20)个,池大小即并发上限;时间轮 pump 按同一个数限流,池里不会排队。
  • 按 did 串行:同一条 RS485 总线上的方法不能并发,由时间轮的 busyDevices 保证。
为什么不用 vertx.setPeriodic

它回调跑在 event loop 上,而调度步要读库(对账、认领租约、写结果),在 event loop 上 await() 会被 Quarkus 直接拒;轮询也完全不需要 event loop 的低延迟。停机时 stop 等手续收尾, 不释放租约——被中断的那一帧可能已在总线上,让租约自然到期比立刻放给别人重发安全。

⑥认领与多副本:同一个客户端

ModbusPollingRepository.claim 做一件事:能抢则原子地「租约 + 前推 nextRunAt + 记 lastRunAt」。 抢不到的那次调用不是失败——它说明另一个副本正跑着这条,直接重排即可。判据: 租约已过期(leaseUntil 空或已过)或持有者就是自己(上一次没放干净,重入同一任务不该被自己挡住)。 停机不释放租约,代价是停机后最多 lease-seconds 缺省 60s 的空窗,换来「帧可能已在总线上」的安全。

⑦接口:查任务和运行时状态

GET /matrix/v1/modbus/polling/{spaceId},空间成员可访问。返回该空间下所有服务的轮询任务: {spaceId, enabled, instanceId, queueSize, busyDevices, inFlight, lastTickAt, items: [...]}。

  • items:任务行 + 运行时状态,服务名一起带(前端不必再查定义才知道这条任务是谁的)。
  • 任务表里没有的方法不出现——没配周期或被 polling=false 关掉的方法就不该有任务, 与「有任务但很久没跑」不是一回事(后者 lastRunAt 会说话)。
  • 内存读数是本进程的:poller 与 api 是同一份代码的两个部署,问到 api 副本时 items 照旧对(读库), 但 queueSize 一定是 0——它不跑调度。看「谁在采」要问 poller 那个副本,或看每条任务的 leaseOwner。

⑧对账:幂等重算,不做增量事件

ModbusPollingReconciler 让 modbus/polls 与内存时间轮跟着服务定义走。它做的是幂等的从 modbus.services 全量重算, 而不是增量事件——丢了事件、改错了库、poller 停机几天,都能靠下一次对账修回来。两个时机: 写入路径(ModbusServiceService 的 create/update,与影子、告警并列 reconcileDerived)和 调度线程的周期兜底(reconcile-seconds)。库里 nextRunAt 优先:对账不是重排,别把一次采集往后推。

和影子/告警的关联

写入路径 reconcileDerived 一次管三样派生数据:轮询任务(本页)、影子(由 ModbusShadowPlan 判孤儿删,service-shadows 那套)、告警(由 ModbusAlarmReconciler 判陈旧关)。 都是「定义改了就跟着改」的幂等对账,失败只记日志、不让一次定义维护跟着失败。
