ModbusHistory：采了什么，就记什么

读方法一次执行的结果，按落库规则记成历史。这与告警是两件事：那边记「值不对」，这边记 「采到什么」。流畅文档只讲三件事——存哪、怎么写、怎么读。完整规则见 Modbus-History.md,这里是对着当前代码走读。

存储 service-registry-histories / service-polling-histories / service-shadows 写 ModbusHistoryWriteService 判定 ModbusHistoryPolicy 读·曲线 ModbusRegistryHistoryService 读·故障 ModbusPollingHistoryService 整形 ModbusRegistryHistoryWindow
一句话记住它

历史是副作用：值已经拿到了,才去记它。写挂在采集链路的 record(成功)与 recordFailure(失败)两个入口,手动 invoke 和轮询走同一个入口;读有两个接口: 一只寄存器的区间曲线(/registry/range)和整个空间的故障清单(/polling/failures)。

①先看全貌：写、存、读

下面一张图串起「采集 → 落库 → 读取」。后三节分别展开 存(三张表)、写(判定 + 影子不变量)、 读(两个接口 + 窗口整形)。

图 1 · 采集如何落成三张表，以及两条读接口各自读哪一张

②存了三张表，主角是「逐寄存器」的

历史从「按方法」迁移成「逐寄存器」：一条历史事件就是一个寄存器的一次出值。定位一看就懂—— 曲线按点取、当前值按影子取、操作按日志取。

集合实体一条是什么关键字段TTL
service-registry-histories ModbusRegistryHistory 一只寄存器的一次事件（成功值 / 失败标记） serviceId, registerIndex, name, unit, at, value, failure, message ✅ 缺省 90 天
service-polling-histories ModbusPollingHistory 一次调用（操作日志,每个调用必落一条） serviceId, pollIndex, operation, ok, type, remoteCode, message, at ✅ 缺省 90 天
service-shadows ModbusShadow 一只寄存器的当前值 / 故障态(不落历史,只当状态) serviceId, registerIndex, value, recordedAt, lastError, errorAt ❌ 不设
三张表各司其职，别混

寄存器历史是给人看的曲线;操作日志记「这轮调用发生没发生、成没成」——它是审计不是曲线, 所以失败统计(filter 清单、byType 汇总)从这里出;影子不是历史,它是「当下状态」,写侧当比对基准、 读侧当当前值。影子没有 TTL:它是状态不是明细,删了当前值就没了。

③怎么写：两条判定,一条不变量

3.1 挂在哪:采集链路里的一处副作用

ModbusServiceService.execute 解出字段后,把 先记历史、再评告警 串起来 (串只是为了顺序确定——历史是「采到什么」、告警是「值对不对」,出问题时先看前者):

.chain(read -> recordHistory(service, poll, read, baselines)   // 这里写 ModbusHistory
        .chain(ignored -> evaluateAlarms(service, poll, read))   // 这里是 ModbusAlarm
        .replaceWith(read));

两者都是副作用:失败只记日志、recoverWithNull,既不改写 invoke 的成功响应、 也不改写失败响应——值已经拿到了。

3.2 影子 / 基准:一条不变量

写之前要拿「上次的值」才知道这次变没变。这个基准(基线)有两个来源,落库规则一份不复制:

  • 手动 invoke:每次都从库里重建(ModbusHistoryWriteService.record 三参版,读影子 → blockBaseline)。 ModbusPollBaseline 就是「字段→值 + recordedAt + lastError」那份基准。
  • 轮询器:用自己的内存基准缓存(ModbusPollBaselines),省掉每次读库—— 单副本才成立;故障态 / 没缓存时 usable 判定为不可用 → 回退到读库。
「先写明细 → 再更新影子」是正确性,不是顺序偏好

反过来的话:明细写失败而影子已经前进,那次变化就永久丢了(下次比较基准已经是新值)。 按现在的顺序,失败时影子停在旧态,下次采集仍判「变了」而重试。失败记录同理:影子留着旧故障, 下次同样的故障仍会被重判并重试落库。ModbusHistoryWriteService.record 的类注释把这个写得很死。

3.3 一次采集,Policy 判定落哪些字段

ModbusHistoryPolicy.decide 逐字段判,三条规则:

规则判据谁靠它
变位值 ≠ 基准值 → 落一条正常样本开关量
死区|值 − 基准值| ≥ deadband 才算变模拟量
保活打点距上次落库 ≥ 保活周期 → 值没变也强制落一条区分「值稳定」和「采集挂了」
死区为什么要有

没有死区,缩放后的温度每次都在变(61.5 → 61.6),压缩率会退化成 0。数值一律按 doubleValue() 比(影子从库读回来可能是 Integer/Long/Double,与本次算的类型未必一致, 按类型比会把「没变」误判成「变了」)。

3.4 成功 record / 失败 recordFailure,各写什么

record 与 recordFailure 各有一对入口(参数多一个的是基准由调用方给), 落库逻辑只实现一份:

入口操作日志寄存器历史影子
record（成功） 每次调用一条(operation = read/write, ok = true) 判为「变了 / 保活」的字段,能解析到寄存器就各追加一条成功事件 各 upsertValue 更新当前值、清故障态
recordFailure（失败） 每次调用一条(ok = false,带 type/remoteCode/message) 该读方法每个可读寄存器各记一条失败事件(曲线竖线) 各 upsertFailure 更新故障态(值/时刻保留上次成功)
  • 操作日志与「值变没变」无关:它记的是「这轮调用执行过、成没成」。所以重复失败也照记, 去重是值历史/影子的取舍——同一场故障(lastError 相同)不再重复落寄存器侧。
  • 写方法(应答为空):没有读值可记,但「这次成功」要落下来——否则上次失败留在影子上的故障态永远清不掉。
  • 上次失败过、这次成功:把这次当「首次采集」处理(基准置空 → 每个字段都落一条)。 否则值恰好没变时,恢复的那一刻一个样本都不落,曲线上分不清「已恢复」和「仍在故障」。
  • 绝大多数采集走「什么都不写」(值没变、没到保活):只落一条操作日志,寄存器历史/影子零操作。

3.5 级联清理

purge 在服务/设备被删时,把四个仓储一起并删除:寄存器历史、影子、操作日志、告警 (与历史同命——服务没了,告警再也没人处理,是存储垃圾)。

④怎么读:两个接口

4.1 一只寄存器的区间曲线

GET /matrix/v1/modbus/history/registry/range/{spaceId},空间成员可访问:

参数语义
serviceId / pollIndex / field点名这条曲线。 field 是寄存器名(逐寄存器后,由服务定义的 registries[] 解析成 registerIndex); pollIndex 为兼容旧前端仍接收、仅忽略。
from / toepoch 毫秒;from 必填,to 缺省 = 到现在。
maxPoints返回点数上限,缺省 500、封顶 2000。

响应:{serviceId, pollIndex, field, from, to, maxPoints, downsampled, total, points, carryIn?}。 points 是原始样本(未超 maxPoints)或降采样桶(超了);carryIn 是窗口起点之前最近那条, 没有就不出键——不带它曲线从起点就是空白。

区间有硬上限,超了报错而不是静默截断

一次最多取回 MAX_ROWS = 20000 条原始样本。超出报错(time range too wide...)—— 截断会把曲线的尾巴悄悄抹掉,前端看起来一切正常;报错至少能让人缩小时间范围。多取一条正是为了判「超了」。

4.2 整个空间的故障清单

GET /matrix/v1/modbus/history/polling/failures/{spaceId},空间成员可访问:

参数语义
serviceId不传 = 整个空间(含子空间):子树下所有服务的失败的调用合成一条倒序清单。
pollIndex / type可筛一个方法、一个故障分类;不传不限。
from / to / limit区间 + 条数(limit + 1 判截断)。

响应:{from, to, limit, truncated, items, summary}。items 按时间倒序; summary 是这批 item 按 byType(分类)与 byRemoteCode(远端原始码)的聚合,两者一起看。

空间级查询 = 逐服务各查一次、再内存归并

与告警/故障清单同一口径:索引以 serviceId 打头,跨服务查等于丢索引前缀做全表扫;一个空间下 服务只有十几条。每个服务取 limit + 1 条,多出来那条用来判「还有更早的没取回来」。

⑤曲线的整形:carry-in、降采样、maxPoints

区间读把原始事件喂给 ModbusRegistryHistoryWindow(纯内存、可单测),它决定: downsampled = true 时点被折叠成桶 {at, until, count, first, last, min, max, avg} (阶梯函数折叠),否则原样给原始样本。历史页与看板字段曲线共用同一份整形—— 数据源一个是寄存器历史服务、一个是看板的字段曲线,响应是同一份形状、同一套 points/carryIn/downsampled 分流,前端 `decodeRange` 只写一份。

carry-in 为什么必须是「成功」事件

失败事件没落到值。曲线从窗口起点的状态,由from 之前最近一条成功续上; 若那是失败,就当「这次没有更早的样本」——否则会把一段「离线」画成一段「值」。

⑥保留:TTL 只管明细,不管状态

modbus.history.retention-days 缺省 90 天(不设 env 也生效,部署起就开始删 90 天前明细; 想先观察就显式设 0)。由 ModbusHistoryRetention 把天数翻译成 TTL 秒数,落到寄存器历史与操作日志 两个集合的 at 上建 expireAfter 索引;影子不挂 TTL。

存储的是 Azure DocumentDB(Postgres 底)

它跑在开源 DocumentDB 引擎上、不是 MongoDB 本体。服务端认不认「自定义字段上的 TTL」只能实测 (Modbus-History.md 第六节有冒烟)。ModbusHistoryRetention 只算口径、不管能不能删, 仓储照既有索引方向 Action 执行。
