01范围与结论

三条线，一套统计底座

设计稿把能源分成消耗、生产、存储三个页面。实现上它们不是三套逻辑，而是同一份「配置 → 采样 → 小时桶 → 报表」底座上的三个角色：数据形状一样，只是指标和页面重点不同。

角色页面重点核心指标
CONSUMPTION
能源消耗		 用量报表、费用、同比环比 用量 energy、成本 cost
PRODUCTION
能源生产		 产量报表、收益、同比环比 产量 energy、收益 revenue
STORAGE
能源存储		 实时状态卡、SOC / 功率曲线、充放电吞吐、效率与套利 充电量、放电量、SOC、功率、容量、循环次数

这一版交付了后端 /matrix/v1/energy 的配置增删改查、报表、实时状态与摘要，EnergySampler 定时采样；前端 /main/energy 一级摘要页（五张卡、三块用量与存储状态）、按角色拆开的三个二级页（要点卡、图表、逐桶表格、管理员配置对话框、导出），以及 66 份词典的能源词条补齐。

三个影响全局的取舍

存储只落小时桶
天和月都是小时的整数倍。 采样线程只往小时桶累加，报表读出来再在内存里汇总。配置里的 periodHours 不改变数据形状，避免历史库里混着 1 小时桶和 4 小时桶。
粒度由服务端按跨度选
前端只给 [from, to)，不传粒度。 两天以内看小时，两个月以内看天，再长看月。页面上的「今天 / 本月 / 跨年」因此不需要各自记住一套参数。
实时状态单独接口
报表桶里的 SOC 是平均或末值，给不出「现在」。 状态卡直接读点位基线（energy-point-states）的最后一个读数，再配当天的充放电合计。

02数据模型

配置属于项目，点位指向读数

一条配置是「一个项目 × 一个角色 × 一个能源类型」的统计口径。点位可以挂在项目下任意子空间的设备上，但配置本身只属于项目根空间 —— 与设备、服务、看板的「按项目」口径一致。

集合一条记录是什么关键字段
energy-configs 项目里的一条统计配置 spaceId（根空间）、role、type、points[]、价格、periodHours、enabled
energy-stats 一条配置的一个小时桶 累计量用 $inc；SOC 存和与次数、极值、末值；容量类只存末值
energy-point-states 一条配置里一个点位的累计基线 lastRaw、lastAt、total、updatedAt

点位身份：key 不含名字

点位在服务端没有独立 id，身份由「来源 + 设备引用 + 指标」拼成。名字和单位只是展示，改名不会让累计基线断掉；反过来，同一个读数配两遍会被校验拒绝 —— 否则电量会被计两次。

// EnergyPoint.key()
SERVICE  | did.siid.piid       | ENERGY
REGISTER | fdid#registerIndex  | SOC

价格与校验

  • 消耗 / 生产用 price；存储用 chargePrice 与 dischargePrice。价格为空是「不算」，不是「算出来是 0」。
  • periodHours 只允许 1 / 4 / 12 / 24；价格不能为负；角色与指标必须匹配：存储不能用笼统的 ENERGY，消耗 / 生产只能用 ENERGY。
  • 点位字段必须成套：服务属性要有 did / siid / piid，寄存器要有 fdid / registerIndex；电量点位必须声明取值方式。
编辑与删除

更新配置会清空这条配置的点位基线：来源或口径改了以后，旧基线继续用会算出一个错误的差值。删除配置会同时删掉它的小时桶与基线，不留孤儿数据。代价只是编辑到下一次采样之间那一小段增量缺失。

鉴权按空间：读需要项目成员，写需要项目管理员；路径上的 spaceId 可以是项目下任意一级空间，服务端统一归一成根空间再查。

03采样与口径

读数怎样变成电量

采样器每 60 秒把启用配置的点位读一遍。设备属性走影子批量取，寄存器走 Modbus 影子；一条配置或一个点位读失败只影响这一轮，不会让整个循环停摆。

状态卡

三种取值口径

口径读数含义本轮增量边界处理
ACTUAL 累计表底（电表、累计电量寄存器） 本次 − 上次 读数变小视为清零 / 换表：增量取新读数本身；首读只建基线
INCREMENT 读数本身就是增量 本次读数，但同一个读数只算一次 寄存器看 recordedAt 是否变新；服务属性没有时间戳，看值是否变化
POWER 瞬时功率（kW） 功率 × 距上次采样的时长 时长夹在 0 到 3 个采样周期之间；正数算充电，负数算放电

功率积分只在「存储角色且没有配显式充 / 放电量点位」时启用。配了累计充放电寄存器就优先用寄存器，否则两边会重复计电。

设备属性的限制

设备属性影子没有时间戳，只能按「值是否变化」判断是不是一次新上报。代价是连续两次增量恰好相同会被漏掉一次（例如每轮都上报 1 kWh）；这是没有时间戳时唯一安全的选择，比每轮重复累加要好。

一条配置里多个点位怎样合

合并规则按指标性质定，同一轮内先合成一个采样再写桶：电量、充放电量、功率、容量、循环次数相加；SOC、SOH、温度取平均。价格在所采样的那一刻折算成成本 / 收益，之后改价不重算历史桶。

部署开关

配置项默认说明
energy.sample.enabledfalse默认关。只能在一个副本上开，多副本同时采样会把同一段时间重复累加

04报表与聚合

小时桶怎样变成曲线

报表接口接收一个左闭右开的毫秒窗口，按跨度自动选展示粒度，把窗口内的小时桶汇总成密集的展示桶，并同时算本期、环比、同比三个合计。

一小时 60 次采样 1 行 energy-stats
累计量：本轮增量求和 瞬时量：和 ÷ 次数 · 极值 · 末值

粒度与窗口

窗口跨度展示粒度典型页面
≤ 48 小时HOUR今天、昨天、本周
≤ 62 天DAY本月、上个月
更长MONTH跨年自定义区间
  • 窗口最长 366 天；to 不传默认现在；from ≥ to 报错。
  • 展示桶按请求时区对齐：小时取整点、天取本地零点、月取本地 1 日零点，跨夏令时由日期推算，不靠加固定毫秒。
  • 窗口内每个桶都在（密集零填充）：没采到数据的桶值是 0 / null，但 samples = 0，页面据此显示「—」而不是「用量 0」。

合计、环比与同比

环比不是拿本期乘系数，而是再查一次上一等长窗口（[from − span, from)）；同比按本地时间减一年后同样查库。这样「本月至今」的环比自然是上月同期，不会多算几天。

多条配置合并时，先在每条配置内部滚成展示桶，再把同一桶相加：容量和循环次数在配置内取末值，跨配置才相加。顺序反过来会把「每台电池的容量」滚成一台的。

页面上额外算的几个数

  • 充放电效率 = 放电量 ÷ 充电量，只在本窗口内算，不跨周期。
  • 循环次数增量 = 本期末值 − 上期末值，只有配了累计循环数才显示。
  • 套利收益 = 放电收益 − 充电成本；两项价格都没配时返回 null，不显示 0。
  • 变化率：上一期是 0 或没有数据时显示「—」，不编一个 0%。

实时状态卡

/status 只处理存储角色：列出启用中且有点位的配置，每条配置读点位基线的最后读数，加上当天的充放电合计。

  • 一条配置内：SOC / SOH / 温度取平均，容量 / 功率 / 循环次数相加。
  • 多台电池：总览的 SOC / SOH 按容量加权，温度简单平均，其余相加。十度电的电池和一百度电的电池不能同样看待。
  • 停用的配置不出现：基线还留在库里，但把它当「当前状态」只会误导。
  • 缺数据是 null，页面显示「—」。

05接口

七个端点，两种权限

全部挂在 /matrix/v1/energy 下。读需要空间成员，写需要空间管理员；错误沿用全仓的 OxResponse.error（HTTP 200 + success: false），不用 4xx。

方法路径权限说明
GET/configs/{spaceId}成员role、type 可选
POST/configs/{spaceId}管理员新建配置
PUT/configs/{spaceId}/{id}管理员整体替换，清空点位基线
DELETE/configs/{spaceId}/{id}管理员同时删除桶与基线
GET/report/{spaceId}成员role、type、from 必填；to、configId、zone 可选
GET/status/{spaceId}成员type 必填；zone 可选
GET/summary/{spaceId}成员from 必填；to、zone 可选

代码组织

四个模块各占一个子包，资源类按模块拆开、都继承 AbstractEnergyResource（共用按空间鉴权与参数解析）；小时桶、rollup、采样与共享读侧仍在 energy 根包。

api/energy ├─ AbstractEnergyResource 成员 / 管理员判定、枚举与时区解析 ├─ EnergyBucket / EnergyGranularity / EnergyRollup 小时桶与滚动汇总 ├─ EnergySampler / EnergyAccumulator 定时采样与累计 ├─ EnergySeriesReader 报表与摘要共用的读侧 ├─ config/ EnergyConfigService · Codec · Validator · Resource ├─ report/ EnergyReportService · Codec · Report · Resource ├─ status/ EnergyStatusService · Codec · Status · Resource └─ summary/ EnergySummaryService · Codec · Summary · Resource

约定

  • 时间一律 epoch 毫秒，from 含、to 不含，与看板 / 告警一致。
  • zone 是 IANA 时区名；前端传浏览器时区，保证「今天」从本地零点算起。
  • 报表返回 buckets（展示桶）、totals（本期）、previous（环比）、lastYear（同比）和配置摘要。
  • 桶里的功率同时给带符号的 powerMax 和拆开的 chargePowerMax / dischargePowerMax，表格不必自己判断方向。

为什么合计里没有平均 SOC

瞬时量在桶里存的是「和 ÷ 次数」。跨桶再求平均要按各桶的采样次数再加权，否则采样多的时段会被采样少的时段稀释。页面上的平均 SOC 直接由后端的桶值给出，不把各桶平均值再平均一次。

06前端结构

一级摘要 + 三个二级页

一级页（/main/energy）是摘要：页头只有时间范围与刷新，内容通过一次 GET /energy/summary 取回五张总计卡、五组曲线与存储状态。二级页按角色各一个页面组件（consumption/ / production/ / storage/），各自 providers 一份 EnergyFilterStore：页头的类型、时间范围、单条配置与报表读同一份条件。三级「节能」页挂在消耗页下面。二级页的公共部分 —— 页头筛选、报表取数、配置管理、导出 —— 都在 shared/page/energy.report.page.ts 的抽象基类里。

EnergyComponent /main/energy · 摘要 ├─ 时间范围 + 自定义区间 页头 extra · EnergyFilterStore ├─ 五张总计卡 GET /energy/summary · totals[] ├─ 电 / 气 / 水用量 series.consumption / production / gas / water └─ 存储状态卡 storage + charge / discharge + series.storage EnergyReportPage /main/energy/{consumption,production,storage} ├─ 页头：类型 / 时间范围 / 单条配置 / 返回 ├─ 报表 要点卡 · 图表 · 逐桶表格 · GET /report ├─ 实时状态卡 仅存储 · GET /status ├─ 配置选择与编辑对话框 仅管理员 └─ 导出 PDF / Excel / CSV / HTML

取数节奏

条件与请求放在同一个 effect 里：一级页看项目与时间窗口，二级页再加角色、类型与单条配置；刷新版本与每分钟的 tick 也都经窗口参与计算，任一变化就重取，不需要在每个 setter 里记得调一次。一级页取数期间保留上一次结果，晚到的旧响应按请求序号丢弃；二级页同样每分钟推一次时钟 —— 「今天」的终点不该停在打开页面的那一秒。

几个页面约定

  • 一级页只有窗口，不收角色 / 类型 / 配置；五张卡与五组曲线共用同一次请求，不并发拼五个报表。
  • 一级页失败给一条 nz-alert，用右下角刷新按钮重试；没数据时五张卡「—」、图表空白，不显示 0。
  • 只有存储页请求实时状态；切换类型时重置「单条配置」筛选，免得筛出空报表。
  • 配置对话框里用 point.key() 查重，重复点位当场拒绝；编辑时复制点位，不直接改列表里的对象。
  • 非管理员看不到写按钮；按钮隐藏不是权限，后端仍按空间管理员再判一次。
  • 桶里 samples = 0 的整行显示「—」；瞬时量是 null 时显示「—」而不是 0。
  • 图表切换曲线 / 柱状图只改 option，不重取数据。

07多语言

键是中文，值才是译文

08验证

算错不会报错，只能靠用例

能源这一层的错误通常不会让页面崩，只会显示一个看着很合理的数字。因此把纯算术抽出来单测：采样口径、滚动汇总、配置校验、编解码都不依赖 Mongo 或时钟。

09摘要页

一级页从 mock 走到服务端

摘要页（/main/energy）已经从 energy.summary.mock.ts 换成服务端取数：不新建集合，也不让前端拼五个报表，而是由服务端读现有小时桶，一次返回整页需要的数据。

已实现 接口、口径与字段均按本节落地；三个取舍的实际选择见本节末尾，实现落点列在「接口」之前。

一个只读端点
GET /matrix/v1/energy/summary/{spaceId}，成员可读。 只收窗口与时区，不收角色 / 类型 / 配置 / 粒度；整页一次返回，避免前端拼五次报表。
不落摘要表
读时从 energy-stats 聚合。 现有小时桶已是配置 × 小时粒度，摘要只是换一个窗口再滚一次；不新增集合，也就没有失效与回填问题。
code、null、previous
总计用稳定 code；没数据给 null；上一期给原始值。 前端映射词条、用既有 changeRate() 算环比，服务端不掺界面语言与展示格式。

页面上的数据分四块

页面区块需要的数响应字段
五张总计卡 太阳能 / 电池 / 电网 / 燃气 / 用水的窗口合计、单位、环比 totals
电力对比图 用电、发电两组展示桶 series.consumption / series.production
燃气 / 用水图 两组展示桶 series.gas / series.water
存储状态卡 当前 SOC / 可用容量 / 额定容量 / 净功率；窗口内充放电量；SOC 与功率曲线 storage + charge / discharge + series.storage

数据从哪来

全部来自现有三张表，没有新的采集，也没有新的写入：

  • energy-configs 决定「哪些配置算哪一类」：角色 × 类型；
  • energy-stats 提供窗口内的小时桶（energy、charge、discharge、socSum、powerSum…）；
  • energy-point-states 由 EnergyStatusService 读出「此刻」的 SOC、容量与功率。

现有模型没有「太阳能 / 电网 / 电池」这种机器可读的来源字段；EnergySourceKind 表示的是读数来自服务属性还是寄存器，不是能源来源。因此五张卡只能按 角色 × 类型 映射：

总计卡口径取数
太阳能总计生产 × 电力sum(production.energy)
电池总计存储 × 电力，窗口内充电量sum(storage.charge)
电网总计用电 − 自发自用，近似净购电max(0, sum(consumption.energy) − sum(production.energy))
燃气总计消耗 × 燃气sum(gas.energy)
用水总计消耗 × 用水sum(water.energy)
电网是近似值

当前公式只减太阳能，没有再减电池放电，也没有区分购电与上网。它与消耗页的用电合计能对上；要做到真正的「电网购入」，需要给配置加来源语义（如 source = GRID）或单独的电网点位。见本节末尾的取舍。

存取方式：读时聚合，不落摘要表

摘要不单独存一份：窗口、时区、粒度都可以变，存下来就要处理失效、回填和配置编辑；而现有小时桶已经是按配置 × 小时存的，读的时候滚一遍即可。一次请求的路径：

请求spaceId
from / to / zone
→
配置 + 两个窗口按 role × type 分组
本期 + 上一期
→
内存聚合EnergyRollup
rollup / summarize
→
响应总计 + 五组桶
+ 存储状态
  • 本期：窗口内每个配置读一次 energy-stats（现有 findRange(configId, from, to)），按粒度滚成展示桶，再按 EnergyBucket.merge 跨配置合并。
  • 上一期：同样大小的 [from − span, from)，只取合计、不取展示桶，用于环比。和报表「环比不是乘系数」同一条规则。
  • 存储的合并顺序：容量、循环次数必须先在每条配置内滚成末值，再跨配置相加；反过来会把「每台电池的容量」滚成一台。直接复用 EnergyReportService 的 rollup 顺序，不另写一套。
  • 存储状态：复用 EnergyStatusService.status(...).total（启用且有点位的配置，SOC 按容量加权）；窗口充放电量则取本期存储桶的合计，不用 status 里「今日」的充放电。
  • 不写库：整个接口只读，不产生新集合、不更新基线，也不触发采样。

实现上已经把 EnergyReportService 里私有的 buckets() / totals() 抽成了 EnergySeriesReader：报表与摘要共用同一套「按配置读桶 → rollup → 跨配置合并」，EnergySummaryService 只做「按角色 × 类型分组 + 五张卡 + 上一期 + 存储状态」的编排，没有第二份 rollup 规则。也没有在服务层连调 5 次 report() —— 那会重复查上一期与同比、重复取配置。

仓库里还有一个未使用的 EnergyStatRepository.latest(spaceId, role)，注释写着「摘要用」。它是最后一个桶，不如点位基线实时，不要拿它代替状态卡；摘要的当前 SOC / 功率仍走 EnergyStatusService。

读放大与缓存

一次请求读 2N 次桶（N = 项目配置数，本期与上一期各一次），外加存储状态按启用配置读点位基线。现有报表本来就是按配置逐个 findRange，摘要沿用同一量级；五张卡与五组曲线共用这两轮查询，不会乘 5。配置很多时再按顺序优化：

  • 给 EnergyStatRepository 加按 spaceId + bucketAt 范围的查询，利用现有 (spaceId, role, bucketAt) 索引，在内存里按 configId 分组后再滚 —— 一个窗口一次查询，而不是一个配置一次。
  • 确实压不住再加 30 秒 TTL 的进程内缓存，key = spaceId + from + to + zone；窗口终点是「现在」时缓存会短暂滞后，刷新按钮要能绕过。
  • 预聚合的 energy-rollups 只在数据量证明必要时做，不放在第一版。

第一版不加缓存：摘要每分钟刷一次，读的是同一批小时桶，Mongo 的量很小；先把数字正确、失效路径简单放在前面。

接口

方法路径权限参数
GET/summary/{spaceId}空间成员from 必填；to、zone 可选
  • 挂在现有 /matrix/v1/energy 下，沿用 requireSpaceMember；不走管理员。
  • from / to 是 epoch 毫秒，[from, to)；from ≥ to、跨度超过 366 天直接报错，与 /report 同一套校验。
  • zone 是 IANA 时区；前端传浏览器时区，不传则服务端默认时区。展示桶按本地整点 / 零点 / 月初对齐。
  • 不传粒度、角色、类型、配置：摘要固定看项目全量，粒度由服务端按跨度选（≤48h 小时、≤62d 天、更长月）。长窗口会返回 MONTH，前端 bucketLabel() 已支持，不需要另做降级。
  • 响应仍是 OxResponse：成功 success: true，失败 HTTP 200 + success: false。

字段含义空值
totals[].key固定顺序：SOLAR、BATTERY、GRID、GAS、WATER不会缺
totals[].value窗口内合计，按对应口径计算没有配置或没有采样 → null
totals[].previous上一等长窗口的同口径合计null；前端据此算环比，不显示 0%
totals[].unit服务端按类型给的规范单位：电 kWh，气 / 水 m³不会缺
series.*[].at展示桶起点（本地对齐的 epoch 毫秒）不会缺
series.*[].samples该桶采样次数；0 = 没数据不会缺
series.storage[].soc / power桶内 SOC、净功率（正充负放）无采样 → null
charge / discharge窗口内充电量 / 放电量没有存储采样 → null
storage此刻的 SOC / 可用 / 额定 / 净功率没有启用中的存储配置 → null；字段也可能为 null

总计用 code，不用中文。 服务端返回稳定的 SOLAR 等 code，前端映射到已有 i18n 词条，服务端不依赖界面语言，以后加语言也不用改接口。前端映射只有五行：SOLAR → 太阳能总计、BATTERY → 电池总计、GRID → 电网总计、GAS → 燃气总计、WATER → 用水总计。

环比沿用现有分工：接口返回 previous，前端用 energy.ranges.ts 里已有、已有用例的 changeRate(current, previous) 算百分比。这样 /report 与 /summary 对「上一期是 0 或没有数据」的处理完全一致，不在服务端再写一份变化率。

空数据与边界

情况响应页面
某来源没有配置该卡 value = null；电网公式里把缺席的发电按 0 计卡片显示「—」，不显示 0
有配置但窗口内没采样该卡 value = null；桶 samples = 0、值为 0曲线空白，卡片「—」
发电有配置但没采样、用电有数据电网 value = null（不知道自发自用，不能拿用电冒充净购电）电网卡「—」
上一期没有数据或为 0previous = null环比「—」

部署默认 energy.sample.enabled = false，联调时先把采样打开；否则窗口里一个采样点都没有，整页都是「—」，这不是接口故障。

停用配置去哪了

窗口的桶与总计沿用 /report 的口径：包含停用配置的历史桶，这样摘要与消耗 / 生产 / 存储页对同一个窗口的数字一致。存储状态卡沿用 /status 的口径：只算启用且有点位的配置，因为「现在」不该由一台停用的电池代表。两边口径不同是现有实现就有的，不是摘要新造的；如果产品希望摘要只算启用配置，应当同时改 report，否则点进二级页会对不上。

为什么不这样做

备选为什么否掉
前端并发调 5 个 /report + 1 个 /status六次往返，各自算上一期与同比；配置在两次调用之间被改会拼出不一致的一页；电网与电池公式还得前端再写一份。
采样时写一张 energy-summary 表摘要随窗口、时区、粒度变化，预聚合要按这些维度再存一份；配置编辑、改价、停用、回填都会触发失效，写入放大且难补齐。
现在就给配置加 source（太阳能 / 电网 / 电池）五张卡用角色 × 类型已经能映射；加字段要改配置表单、存量数据迁移与校验。等真正需要区分「购电 / 上网」时再做，届时电网公式一起改。

前端怎么接

  • EnergySummary 模型与只解不编的 codec：series.* 解成页面用的五组 EnergyBucket[]，totals 映射成 SummaryTotal，storage 与窗口 charge / discharge 拼成存储卡。
  • shared/energy.summary.ts：code → 词条（五行固定映射），previous 经 changeRate() 得环比；sumUsage() 跳过 samples = 0 的桶，一个采样都没有时返回 null，页面显示「—」。
  • EnergyService.summary(spaceId, from, to) 与 report() 一样带浏览器时区；页面不再 import mock。
  • energy.component.ts 用 effect 取数：条件（spaceId、窗口、刷新时钟）变化时重取；旧数据先留着，请求完成再替换；请求序号丢弃晚到的旧响应；切项目时先清空旧数字。
  • 加载中页头保留，内容区给 nz-spin；失败给一条 nz-alert，复用右下角刷新按钮重试，不新增 i18n 词条；没数据时五张卡「—」、图表空白，不显示 0。

落地时定下的三个口径

1. 电网：按 max(0, 用电 − 发电)，不扣电池放电、不区分购电与上网；2. 停用配置：窗口桶与总计与 report 一致，包含历史桶；存储状态卡只算启用配置；3. 单位：固定电 kWh、气 / 水 m³，不读点位 unit。三条都落在服务端 EnergySummaryService，要改需同时改 /report 与前端映射。

10边界与后续

这版故意没做的事

下面这些不是遗漏，而是当前实现的明确边界。写出来是为了让 review 时能直接判断哪些需要补。

摘要页的电网口径与缓存
摘要已接服务端，但电网仍是 max(0, 用电 − 发电) 的近似；没有缓存，每次请求按配置逐个读本期与上一期。口径与读放大见 09 摘要页。
periodHours 的角色
配置项会保存、展示，也返回给前端，但报表粒度由窗口跨度自动决定，不读它。若要让「统计周期」成为默认展示粒度，需要再加一个显式参数或前端换算。
一台电池 = 一条配置
配置内多点位会合并成一个数，页面上的「单台设备」筛选实际是「单条配置」。要在配置内按设备拆卡片，需要额外的设备维度。
没有峰谷电价
价格是单一价，在采样时锁进桶里。分时电价、需量电费都未实现；历史桶也不会因改价重算。
没有历史回填
新建配置从第一次采样建立基线，之前的用量不会补算；设备属性在离线期间也不会补点。
采样只跑一个副本
energy.sample.enabled 默认关，部署时必须只在一个副本打开，否则同一段增量会被重复累加。这是部署约定，代码没有分布式锁。
没有 TTL
小时桶不会自动过期：一天 24 行 × 配置数，一年约 8,760 行 / 配置。需要长期保留或另做归档策略。
图表没有单测
四张图的 option 构造函数是纯函数，但没有 spec；当前只靠构建与页面手测。窗口与变化率这类容易算错的逻辑已有 16 个用例。
机器译文待校对
除中英与手工调整的繁体用词外，其余语言建议上线前抽查行业术语。
