ModbusAlarm：一次阈值告警的完整生命周期

读方法的出值越过用户配的阈值时落一条告警。这张文档只讲两件事——它怎么被「产生」出来， 以及落地之后被哪些地方「使用」。完整的规则与设计口径见 Modbus-Alarm.md，这里是对着当前代码把它走读一遍。

存储 modbus / service-alarms 判定 ModbusAlarmPolicy 落库 ModbusAlarmWriteService 查询/处理 ModbusAlarmReadService / ModbusAlarmResource 对账 ModbusAlarmReconciler
一句话记住它

「一次越限一条」的边沿事件：正常 → 越限落一条，持续越限不重复落， 回到正常后再越限才算新的一次。「开着」就是状态——某出值上有一条 recoveredAt 为空的告警行，就等于它「正在告警」;不另存一份告警态。

①先看全貌：一条告警的一生

下面是一条告警从配置、产生、读取到被处理/关闭的完整流程。后两节分别展开产生（右上→右下， 红色那条热路径）与使用（对账、查询、处理、级联删除）。

②它长什么样：数据模型

实体 ModbusAlarm，落在 modbus 库的 service-alarms 集合。 一个出值（(serviceId, pollIndex, field)）同时**最多一条**开着。

分组字段含义
坐标 serviceId / pollIndex / field 哪个服务、哪个方法、哪个出值。位区的具名位也出现在 field 上（一位一个结果键）。
openKey 内部标识，serviceId#pollIndex#field。唯一部分索引建在它上面。绝不下发。
ruleId 触发这条的是哪条规则（配置里的规则 id）。绝不下发，只在判定与对账时做身份比对。
触发那刻的
定义快照		 compare / threshold / state 比较方式、数值阈值、= 的取值表状态名（三选其一触发）。
levelINFO / WARN / CRITICAL。
text用户自定义文案。前后端一律原样显示、永不翻译。
unit单位快照（可能 null）。
sample触发那一刻的值（Number 或取值表描述串）。开着期间不刷新。
at越限首次出现的时刻（UTC），持续越限不刷新。
边沿 / 状态 recoveredAt null = 仍在越限——这就是状态本身，不另存一份告警态。
closeType怎么关的：VALUE / DEFINITION / SUPERSEDED / HANDLED。见第五节。
处理回执 handled 是否被用户认领。null / false 都算未处理。
handledBy第一个处理的人；处理时刻取它的 timestamp。
为什么存「触发那一刻的快照」而不是引用

定义是活的、行是不可变的历史。只存引用的话，把阈值从 80 改成 60 会悄悄改写每一条历史告警的含义—— 「当时为什么报」被一次无关的修改编辑掉了。与故障记录存 message 文本而不存错误码同一个道理。

③它是怎么被「产生」的

3.1 规则从哪来：注册表中心，不是应答字段

告警规则挂在注册表中心的每个寄存器上——ModbusService.configSnapshot.registries[]， 每个寄存器有一个 alarms[]（一组规则）加上 name / unit。 ModbusAlarmPolicy.registerRules(service) 把它展开成一张「出值 → 一组规则 → 单位」的判定表：

List<ModbusFieldRule> rules =// field, alarms[], unit
    ModbusAlarmPolicy.registerRules(service);

规则为什么带 id:身份是配置里的 id,绝不用数组下标—— 删掉第 0 条会让第 1 条正开着的告警「静默改嫁」到新的第 0 条,还能把关闭原因记成 VALUE(谎话)。

3.2 挂在哪：采集链路的一处副作用

产生告警的那条路径是采集本身。ModbusServiceService.execute() 读完帧、解出字段之后, 把两件并列的副作用串起来(串只是为了顺序确定,两者互不依赖、各有各的失败重试):

.chain(read -> recordHistory(service, poll, read, baselines)   // 采到什么
        .chain(ignored -> evaluateAlarms(service, poll, read))   // 值对不对
        .replaceWith(read));

evaluateAlarms 与历史同一个壳:失败只记日志、recoverWithNull, 既不改写 invoke 的成功响应、也不改写它的失败响应——值已经拿到了,告警是副产物。 失败不会丢:下一个仍越限的样本会重试插入、下一个仍正常的样本会重试关闭 (两个边沿各自对库幂等,所以这个特性不需要故障记录那套「先明细后影子」的顺序不变量)。

3.3 判定：纯函数,零库操作

ModbusAlarmWriteService.evaluate 的完整流程:

  1. 第一层闸门 hasEnabledAlarm(rules):纯内存判断。没配告警的服务(绝大多数)在这里返回, 一次数据库操作都不做。
  2. 一次带索引读 mapOpenRuleByField(serviceId, pollIndex):把「这个方法当前哪些出值开着、 各是哪条规则开的、处理过没有」一次查回来,投影只有 field/ruleId/handled。 一个方法配 3 个字段也只查这一次。
  3. 纯函数判定 ModbusAlarmPolicy.decide(rules, sample, open):产出该开哪些、该关哪些。 无状态、可独立单测,比对的是解析后的值(阈值按工程单位)。
  4. 落库 apply(...):按边沿写出动作。

判定是三态而不是两态:HIT / MISS / SKIP(判不了)。 SKIP 必须区别于 MISS——一次截断/畸形的应答不能把一条开着的告警关掉(那是凭空恢复), 它在 apply 里什么都不做、只进日志(WARN)。

3.4 选举:一个出值一组规则,一次采样只留最严重一条

一个出值可以配一组分级规则(低于 20 告警 / 超过 26 提示 / 超过 28 警告 / 超过 30 严重),但同时最多一条开着。 命中多条时只留一条——级别最高的;级别相同则取声明顺序里靠后的那条。 于是不变式「一个出值同时最多一条开着」恰好就是唯一部分索引强制的东西, openKey 因此仍然只有出值、不带规则标识。

3.5 落库:先关、后插——顺序是语义的一部分

apply 把一次评估的动作分两段串起来:先并发关、再并发插。

return all(closes).chain(() -> all(opens));   // 顺序不能靠 ops 列表——combine().all() 是并发的

同一个出值可以「既关又开」(命中了另一条规则 ⇒ SUPERSEDED;开行的规则没换但已被处理过 ⇒ HANDLED)。 反过来(先插后关)时,新行会撞上唯一部分索引,被 insertOpen 当成「别的副本先开了」静默吞掉 (11000),于是这个出值一条开着的都没有——下一轮会自愈,但那个窗口里告警是消失的, 轮询一停就永久丢。这条顺序用 InOrder 单测钉住。

并发护栏:唯一部分索引

poller(1 副本)与 API 副本(N 个)可能同时判定同一 (service, poll, field):两边都读到 「没有未恢复的告警」→ 都插入。解法:插入带 openKey,靠 {openKey: 1} unique + partialFilter 挡第二条;捕获 11000 当作「别的副本先开了」 吞掉(吞掉之后不变式恰好还成立,所以这不是妥协)。关闭用按整个开行标识的 updateMany, 天然幂等。

④它的四种「关闭」与触发线

closeType 四个值覆盖全部关闭路径,互斥:

值何时页面文案
VALUE值回到不命中任何规则值恢复
SUPERSEDED当前生效的是同一出值的另一条规则(升级或降级)被取代
DEFINITION定义不再覆盖这个键:出值被删、规则被删、或该出值所有规则都被停用定义变更
HANDLED这条已经被处理过、而那条规则还在命中:关掉它、另开一条未处理的新行处理后再报
HANDLED:「处理」是「我知道了,以后还有越线再提醒我」,不是「到此为止」

没有这条边沿时,一条已处理而未恢复的行会一直挂着、把后续越线全挡在门外——用户再也收不到提醒,与他的本意正好相反。 于是把 handled == true 也当一个边沿:关掉这条,同时另开一条 handled=false 的新行。 新行的 at 与旧行的 recoveredAt 取同一个 now(一次评估里的所有动作共用一个时刻), 读起来就是「这一刻旧的了结、新的开始」。回执不继承——新的一条要重新处理。

不做防抖 + 永久保留 = 触发线(第十节)

一个在阈值附近来回抖的模拟量,按 5 秒周期每天可以产生上千条永不删除的告警。 触发线:实测若某个服务日均告警 > 100 条,回来加回差（deadband）。会不会回头加防抖,是个有据可依的决定。

⑤落地之后,它被谁「使用」

使用分两类:一类是读与改的对外接口(前端告警页),一类是后端自己的维护(定义变更对账、级联删除)。

5.1 读取:告警清单

GET /matrix/v1/modbus/alarm/many/{spaceId},空间成员可访问。参数可筛 serviceId / pollIndex / field / level / open / handled / from / to / limit:

  • 不传 serviceId = 整个空间(含子空间):把子树下所有服务的告警合成一条时间倒序的清单, 每条自带 serviceId。一条请求顶掉前端逐服务的扇出——告警页要的正是「这个项目现在哪儿在告警」。
  • open / handled 不传 = 不限;它们的 null 与 false 必须区分 (「只看已恢复」不能等于「不限」),所以类型用 Boolean 而非 boolean。
  • 空间级查询 = 逐服务各查一次、再内存按 at 归并:理由与故障清单同——索引以 serviceId 打头,跨服务查等于全表扫。每个服务取 limit + 1 条,多出来的那条就用来判 「还有更早的没取回来」(truncated)。
运维口径:盯「只看未恢复」那张视图

open = true 恰好等于「当前生效的告警」——一个出值同时最多一条开着。而 未处理计数可以大于它, 这不是 bug:被取代的行(SUPERSEDED)仍然算未处理,那是如实的(确实报过、确实没人处理过)。 要清掉它们,用「未处理」筛选逐条点处理;别指望 open 替你把它们筛掉。

5.2 处理(回执)

POST /matrix/v1/modbus/alarm/handle/{spaceId}/{id},无 body,处理人取当前账号;返回更新后的那条, 前端就地替换、不整页刷新。三件值得记的口径:

  • 写之前先判归属:路径上的 spaceId 只证明你是成员,不证明这条告警属于这个空间。判法是 「这条告警的 serviceId 在 subtreeServiceIds(spaceId) 里吗」——与列表查询共用同一个函数, 于是「列表里看得到的就能点」恰好成立。
  • 「已经处理过了」算成功,不算错:CAS 改动为 0 时再读一次,行在就照常返回它(记一条日志)、行不在了才 not found。 那一次读就是为了分辨这两种解释。
  • handledBy 记的是第一个处理的人:仓储那条 updateOne 的过滤条件带 {handled: {$ne: true}},后点的不会把前一个顶掉。

5.3 后端维护:定义变更对账

采集侧的自愈有一条够不着:规则被删、方法被删、或方法不再采,那条还开着的告警再也判定不到、永远挂着。 由 ModbusAlarmReconciler 兜,两个时机、同一个实现:定义变更(写入路径,只取该服务的开行)与 启动(全服务 × 全开行,兜「直接改库绕过写入路径」的残留)。

  • 判据是纯函数 ModbusAlarmPlan:「按新定义,这个 (方法序号, 出值名) 上还有没有一条 id 等于这行 ruleId、且启用着的规则」,找不到的按 DEFINITION 关。 判据细到规则,不是停在出值——否则删掉「超过 30 严重」那条,按它开出来的行会被判成「还覆盖着」而永远留着。
  • 对不认识的服务一律不动:写入路径只传一个服务,这条拦的是将来某个调用方传半份服务列表时的误关。
  • 行上没有 ruleId 的一律不动:关闭是不可逆的动作,宁可留着,交给采集侧的胜者比对按 SUPERSEDED 接手。
  • 只写库、不动内存,所以在哪个副本上改的定义,关就在哪个副本上落库。

5.4 后端维护:级联删除

服务或依赖设备被删时,ModbusHistoryService.purge 把影子、历史、故障与告警一起 deleteByServiceIds真删,而不是按 DEFINITION 关掉。理由:定义变更的「关掉」语义是 「这条告警的原因已不存在」,那是给人看的历史、得留着;而服务整个没了的时候,那条告警再没人能处理、也没人需要 「当时为什么报」——它就是存储垃圾。真正该保留的「这个点位历史上报过什么」在历史与故障记录里另有其份。

三条纪律串起整个写侧(仓储里)
  • 库里没有一条整文档替换:行落下之后只有两种改动——关闭(写 recoveredAt/closeType、$unset openKey) 与处理(写 handled/handledBy),是互不相交的字段,各写各的 $set,谁也盖不掉谁。
  • 关闭按整个开行标识 updateMany,不定位到某条 _id:消除了「幽灵告警永远关不掉」, 采集热路径也只需要「存在性」而不需要身份。关闭只能写 $unset openKey,绝不能 $set openKey: null ($exists 对 null 成立,会让第二条这样的行撞唯一索引)。
  • 处理用 updateOne 绝不 replaceOne:替换会抹掉并行的关闭刚写的 recoveredAt; 过滤带 {handled: {$ne: true}} 让重复点击只生效一次。

⑥把「产生」与「使用」对上

一句话收尾:产生靠采集链路上的 ModbusAlarmWriteService.evaluate——规则从注册表中心来,判定是 开着的行就是状态、一次越限一条、先关后插、唯一部分索引扛并发;这几条拼起来,保证「一个出值同时最多一条开着」。 使用到 ModbusAlarmResource 读(一条请求看完整个空间哪儿在告警)、 ModbusAlarmWriteService.handle 写回执、ModbusAlarmReconciler 在定义变更与启动时清残留、 purge 真删随服务消失的告警。两边的接口都对着 同一份不可变的行——快照保历史, 边沿字段就是状态。

本文档由代码走读生成,与 Modbus-Alarm.md 同源。命名的两处口径:这里「开着 / 产生 / 使用」单指 openKey 有值(未恢复)这一状态;规则身份一律用配置里的 id,不是数组下标。
